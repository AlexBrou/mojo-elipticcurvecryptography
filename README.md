# secp256k1 in Mojo

A port of [libsecp256k1](https://github.com/bitcoin-core/secp256k1) to Mojo,
with a CPU implementation that tracks the C library's algorithms and a GPU path
for batch work.

Every test vector in `tests/vectors/` is generated by a C program
(`tools/gen_vectors.c`) that links against libsecp256k1's own internals, so the
Mojo code is checked against the reference implementation at every layer —
field, scalar, group, scalar multiplication, hashing, and ECDSA — not just at
the public API.

## Layout

```
src/secp256k1/
  field.mojo     field arithmetic mod p, 5x52 limbs (matches field_5x52)
  scalar.mojo    scalar arithmetic mod n, 4x64 limbs
  modinv.mojo    safegcd modular inversion (port of modinv64)
  group.mojo     curve points, affine and Jacobian
  ecmult.mojo    k*G, k*P, and na*A + ng*G (wNAF + GLV endomorphism)
  ecdsa.mojo     sign, verify, recover, DER
  api.mojo       Secp256k1 — keys, tweaks, ECDH, signatures
  gpu32.mojo     the same arithmetic in 32-bit limbs, for GPU kernels
  gpu.mojo       GPU kernels and the batch host API
  scrub.mojo     volatile wipes, for clearing secrets after use
vendor/mojo-sha256/   SHA-256, HMAC and RFC 6979 (git submodule)
ffi/capi.mojo         C ABI wrapper, for use from other languages
include/              the C header for that ABI
examples/             C, Python and Node programs that call the shared library
Dockerfile            library image (125 MB): the shared library and nothing else
Dockerfile.examples   adds Python and Node, to run the FFI demos
Dockerfile.bench      adds the C and Rust toolchains, to benchmark against
tools/gen_vectors.c   regenerates tests/vectors/ from the C library
bench/                benchmarks, and a script that diffs them against C
```

## Requirements

Mojo 1.0 and the `max` package, both installed through
[pixi](https://pixi.sh) — `pixi install` reads `pixi.toml`.

Hashing comes from [mojo-sha256](https://github.com/AlexBrou/mojo-sha256),
pinned here as a git submodule. Clone with it, or fetch it afterwards:

```
git clone --recursive https://github.com/AlexBrou/mojo-elipticcurvecryptography
# or, in an existing clone:
git submodule update --init --recursive
```

Everything on the build path passes `-I vendor/mojo-sha256/src`. `run_tests.sh`
checks the submodule is present and says so plainly if it is not.

Comparing against the C library — the benchmarks, the interop example, and
regenerating the test vectors — needs libsecp256k1 built locally:

```
./tools/fetch_reference.sh
```

The generated vectors are committed, so the test suite itself runs without it.

If you would rather not install a toolchain, `docker build -t secp256k1-mojo .`
builds and tests the whole thing in a container and leaves a 125 MB image with
just the library in it; see [Docker](#docker) below.

The GPU path additionally needs Apple's Metal toolchain:

```
xcodebuild -downloadComponent MetalToolchain
```

Without it, kernel compilation fails with "Metal Compiler failed to compile
metallib".

## Running

```
./run_tests.sh          # every test module
pixi run bench          # CPU benchmarks
./bench/compare.sh      # CPU benchmarks side by side with C, then the GPU ones

cd bench/k256 && cargo run --release   # the Rust comparison (needs a Rust toolchain)

SECP256K1_SKIP_GPU=1 ./run_tests.sh   # everything except the GPU tests
```

`run_tests.sh` must run from the repository root: the vector files are resolved
relative to the working directory.

To regenerate the vectors after changing `tools/gen_vectors.c`:

```
R=reference/secp256k1
clang -O2 -o /tmp/gen_vectors tools/gen_vectors.c \
  -I$R/src -I$R/include -I$R -DECMULT_WINDOW_SIZE=15 -DECMULT_GEN_KB=64 \
  -DENABLE_MODULE_RECOVERY=1 $R/src/precomputed_ecmult.c $R/src/precomputed_ecmult_gen.c
/tmp/gen_vectors
```

## Dependencies

Hashing lives in a separate package, [mojo-sha256](https://github.com/AlexBrou/mojo-sha256),
rather than in this repository. Two reasons: SHA-256 has nothing to do with
elliptic curves and is useful on its own, and it needed a hardware backend that
was worth building and testing properly rather than inlining here.

That backend is why signing reaches parity with the C library. RFC 6979 runs
about 22 SHA-256 compressions per signature, and the package uses the ARMv8
crypto extension where available — roughly six times the portable code. Before
the import, `ecdsa_sign` was 1.31x libsecp256k1; after it, 1.00x.

## Using it

### From Mojo

```mojo
from secp256k1.api import Secp256k1

def main() raises:
    var ctx = Secp256k1()          # builds the generator table; make one and keep it
    var pub = ctx.pubkey_create(seckey32)
    var sig = ctx.sign(msg32, seckey32)
    var ok = ctx.verify(sig[0], msg32, pub[0])
```

Batch work on the GPU:

```mojo
from secp256k1.ecmult import EcmultGenContext
from secp256k1.gpu import GpuBatch

var gpu = GpuBatch(EcmultGenContext())
var points = gpu.mul_gen(scalars)              # k*G for the whole batch
var results = gpu.verify(sigs, msgs, pubkeys)  # one bool per signature
```

Another Mojo project consumes this the way it would any Mojo package: point the
compiler at `src/` with `-I`, or precompile with
`mojo precompile src/secp256k1 -o secp256k1.mojopkg`. Note that a `.mojopkg` is
tied to the compiler version that produced it, so it is not a distribution
format.

### From C, Python, Node, or anything else with an FFI

`ffi/capi.mojo` exports a C ABI, so the library builds into an ordinary shared
object with plain C symbols — the same way libsecp256k1 is consumed:

```
mojo build --emit shared-lib -I src -o libsecp256k1_mojo.dylib ffi/capi.mojo
```

Use `.so` instead of `.dylib` on Linux. Declarations are in
[`include/secp256k1_mojo.h`](include/secp256k1_mojo.h). The conventions match
libsecp256k1: 1 for success and 0 for failure, buffers allocated by the caller,
and a context created once and reused (it holds the precomputed generator
table, so building one is not cheap).

Exported functions:

| Function | Purpose |
|---|---|
| `secp256k1_mojo_context_create` / `_destroy` | lifecycle |
| `secp256k1_mojo_ec_seckey_verify` | is this 32-byte value a valid key |
| `secp256k1_mojo_ec_pubkey_create` | 33-byte compressed public key |
| `secp256k1_mojo_ec_pubkey_create_uncompressed` | 65-byte form |
| `secp256k1_mojo_ec_pubkey_parse` | parse 33 or 65 bytes, re-emit uncompressed |
| `secp256k1_mojo_ecdsa_sign` | RFC 6979 signature, 64 bytes of r\|\|s |
| `secp256k1_mojo_ecdsa_sign_recoverable` | the same, plus a recovery id |
| `secp256k1_mojo_ecdsa_verify` | verify r\|\|s (rejects high s) |
| `secp256k1_mojo_ecdsa_recover` | recover the signer's public key |
| `secp256k1_mojo_ecdsa_signature_to_der` | DER encoding |
| `secp256k1_mojo_ecdh` | raw shared point — hash it before use |
| `secp256k1_mojo_ec_seckey_tweak_add` / `_mul` | tweak a key in place |

#### One caveat before you ship it

A Mojo shared library is **not** a standalone artifact the way a C one is. It
links against Mojo's runtime:

```
$ ldd libsecp256k1_mojo.so
    libKGENCompilerRTShared.so   => .../.pixi/envs/default/lib/...
    libAsyncRTMojoBindings.so    => ...
    libAsyncRTRuntimeGlobals.so  => ...
    libMSupportGlobals.so        => ...
    libstdc++.so.6, libgcc_s.so.1
```

Those five files are about 27 MB and have to travel with it — put them next to
the library, or somewhere on the loader path. The Dockerfile does exactly this:
it runs `ldd`, copies the resolved Mojo libraries out of the toolchain, and
leaves the ~900 MB toolchain behind. Plan for the same in any deployment.

#### C

```c
#include "secp256k1_mojo.h"

secp256k1_mojo_ctx ctx = secp256k1_mojo_context_create();

unsigned char pub[33], sig[64];
if (!secp256k1_mojo_ec_pubkey_create(ctx, pub, seckey)) { /* bad key */ }
if (!secp256k1_mojo_ecdsa_sign(ctx, sig, msg32, seckey)) { /* failed */ }
int ok = secp256k1_mojo_ecdsa_verify(ctx, sig, msg32, pub, 33);

/* recover the signer from a recoverable signature */
unsigned char rsig[64], recovered[33];
int recid;
secp256k1_mojo_ecdsa_sign_recoverable(ctx, rsig, &recid, msg32, seckey);
secp256k1_mojo_ecdsa_recover(ctx, recovered, rsig, recid, msg32);

secp256k1_mojo_context_destroy(ctx);
```

Link with `-lsecp256k1_mojo`. [`examples/use_from_c.c`](examples/use_from_c.c)
does all of this and cross-checks every result against libsecp256k1 in the same
process — the signatures come out byte-identical, since both implement RFC 6979
the same way. Run it with `./examples/build_and_run.sh`; it is also part of
`./run_tests.sh`.

#### Python

No Mojo needed on the Python side — this is plain `ctypes`:

```python
import ctypes
from ctypes import POINTER, c_char, c_int, c_void_p

lib = ctypes.CDLL("./libsecp256k1_mojo.dylib")
buf = POINTER(c_char)

# Declaring these is not optional: without argtypes, ctypes assumes int
# arguments and truncates the 64-bit context pointer on the way in.
lib.secp256k1_mojo_context_create.restype = c_void_p
lib.secp256k1_mojo_ec_pubkey_create.argtypes = [c_void_p, buf, buf]
lib.secp256k1_mojo_ecdsa_sign.argtypes = [c_void_p, buf, buf, buf]
lib.secp256k1_mojo_ecdsa_verify.argtypes = [c_void_p, buf, buf, buf, c_int]

ctx = lib.secp256k1_mojo_context_create()

pub = ctypes.create_string_buffer(33)
lib.secp256k1_mojo_ec_pubkey_create(ctx, pub, seckey)

sig = ctypes.create_string_buffer(64)
lib.secp256k1_mojo_ecdsa_sign(ctx, sig, msg32, seckey)

ok = lib.secp256k1_mojo_ecdsa_verify(ctx, sig, msg32, pub, 33) == 1
lib.secp256k1_mojo_context_destroy(ctx)
```

[`examples/use_from_python.py`](examples/use_from_python.py) wraps the whole
ABI in a `Secp256k1` class with a context manager, covering signing, recovery,
DER, ECDH and tweaks:

```python
with Secp256k1() as ctx:
    pub = ctx.pubkey(seckey)
    sig = ctx.sign(msg32, seckey)
    assert ctx.verify(sig, msg32, pub)

    rsig, recid = ctx.sign_recoverable(msg32, seckey)
    assert ctx.recover(rsig, recid, msg32) == pub

    shared = ctx.shared_secret(pub, seckey)     # hash this before using it
```

Run it with `LIBSECP256K1_MOJO=/path/to/lib python3 examples/use_from_python.py`.

#### Node

Node has no stable built-in FFI, so the example uses
[koffi](https://koffi.dev), which works on Node 18+ and needs no build step:

```js
import koffi from 'koffi';

const lib = koffi.load('./libsecp256k1_mojo.dylib');

// koffi wants the C signatures spelled out. `_Out_` marks buffers the library
// writes into, so koffi copies the result back to the JS side.
const ctxCreate = lib.func('void *secp256k1_mojo_context_create()');
const pubkeyCreate = lib.func(
  'int secp256k1_mojo_ec_pubkey_create(void *ctx, _Out_ uint8_t *out33, uint8_t *seckey32)',
);
const sign = lib.func(
  'int secp256k1_mojo_ecdsa_sign(void *ctx, _Out_ uint8_t *sig64, uint8_t *msg32, uint8_t *seckey32)',
);
const verify = lib.func(
  'int secp256k1_mojo_ecdsa_verify(void *ctx, uint8_t *sig64, uint8_t *msg32, uint8_t *pubkey, int pubkeylen)',
);

const ctx = ctxCreate();
const pub = Buffer.alloc(33);
pubkeyCreate(ctx, pub, seckey);

const sig = Buffer.alloc(64);
sign(ctx, sig, msg, seckey);

const ok = verify(ctx, sig, msg, pub, 33) === 1;
```

[`examples/node/index.js`](examples/node/index.js) exports a `Secp256k1` class
over the same ABI:

```js
const ctx = new Secp256k1();
const pub = ctx.publicKey(seckey);
const sig = ctx.sign(msg, seckey);
ctx.verify(sig, msg, pub);                     // true

const { signature, recoveryId } = ctx.signRecoverable(msg, seckey);
ctx.recover(signature, recoveryId, msg).equals(pub);   // true
ctx.close();
```

```
cd examples/node && npm install && node index.js
```

#### Anything else

The ABI is plain C, so Go (cgo), Ruby (`ffi`), C# (P/Invoke), Java (JNA or the
Panama FFI) and the rest all bind to it the same way. Those are not included as
examples here, but the header is all a binding needs.

### What is not exported

The GPU batch API is Mojo-only. Its inputs and outputs are lists of points and
scalars rather than flat buffers, so exposing it over a C ABI needs a
batch-shaped interface (arrays of 32-byte keys in, arrays of 33-byte points
out) that has not been written yet.

## Docker

Three images in three files, so that what each one drags in stays out of the
others.

| File | Image | Size | Contents |
|---|---|---:|---|
| `Dockerfile` | `secp256k1-mojo` | 125 MB | the library, and nothing else |
| `Dockerfile.examples` | `secp256k1-mojo-examples` | 385 MB | the above, plus Python and Node |
| `Dockerfile.bench` | `secp256k1-mojo-bench` | 2.9 GB | the C and Rust toolchains, to compare against |

### The library — `Dockerfile`

The shared library, the Mojo runtime libraries it links against, the C header,
and a known-answer smoke test. No interpreters, no reference library, no
toolchain:

```
docker build -t secp256k1-mojo .
docker run --rm secp256k1-mojo          # runs the smoke test
```

To use it from another image, copy the two directories across:

```dockerfile
COPY --from=secp256k1-mojo /usr/local/lib     /usr/local/lib
COPY --from=secp256k1-mojo /usr/local/include /usr/local/include
RUN ldconfig
```

That is all a downstream C program needs: `clang -o app app.c -lsecp256k1_mojo`.

The build is two-stage. The first installs the Mojo toolchain through pixi,
clones and builds libsecp256k1, and runs `./run_tests.sh` — so **a build
failure means a test failure**, not just a compile error. The second keeps only
what is needed to run: 125 MB against the 2.9 GB the toolchain alone occupies.

### The demos — `Dockerfile.examples`

Builds on the library image, adding the interpreters the FFI examples need:

```
docker build -t secp256k1-mojo .                            # required first
docker build -f Dockerfile.examples -t secp256k1-mojo-examples .
docker run --rm secp256k1-mojo-examples                     # Python and Node
docker run --rm secp256k1-mojo-examples python3 examples/use_from_python.py
docker run --rm secp256k1-mojo-examples node examples/node/index.js
```

Almost all of the extra 260 MB is `nodejs` and `npm`, which is the whole reason
this is a separate file.

The C example is not in this image: it links against libsecp256k1 as well, to
cross-check every result, and the library image deliberately does not carry
that. Run it with `./examples/build_and_run.sh` on the host, or in the dev
image below, where `./run_tests.sh` covers it.

### The benchmarks — `Dockerfile.bench`

Comparing against C and Rust means carrying both toolchains, which have no
business in a runtime image:

```
docker build -f Dockerfile.bench -t secp256k1-mojo-bench .
docker run --rm secp256k1-mojo-bench                       # Mojo vs C
docker run --rm secp256k1-mojo-bench ./bench/k256/run.sh   # Rust k256
```

Both build caches are warmed during the image build, so `docker run` measures
rather than compiles. Numbers from a container track the host closely (verify
came out at 1.53x against 1.47x on the host), but containers add scheduling
noise — run on the host for anything you intend to quote.

### Development

The builder stage of `Dockerfile` has the full toolchain and the reference
library, so the whole suite runs there:

```
docker build --target builder -t secp256k1-mojo-dev .
docker run --rm secp256k1-mojo-dev ./run_tests.sh
docker run --rm -it secp256k1-mojo-dev bash
```

### GPU in containers

The GPU tests and the GPU benchmark are skipped in all three images. Metal is
not passed through to Linux containers, so on macOS there is no device to
target and `SECP256K1_SKIP_GPU=1` is set. On a CUDA host you can drop that and
run with `--gpus all`, though the kernels have only ever been exercised on
Apple silicon — the 32-bit limb arithmetic is portable, but nothing about the
launch configuration has been tuned for NVIDIA.

The same variable works outside Docker, for both the tests and the benchmarks:

```
SECP256K1_SKIP_GPU=1 ./run_tests.sh
SECP256K1_SKIP_GPU=1 ./bench/compare.sh
```

## Performance

Measured on an Apple M2 (macOS 26.6), against libsecp256k1 built at `-O2` with
the same compiler. Times are microseconds per operation; each figure is the
minimum over three runs of both suites, since the machine is noisy enough that
a single run moves numbers by 30%. Lower is better, and a ratio below 1.00x
means the Mojo port wins.

| Operation | C | Mojo | Mojo/C |
|---|---:|---:|---:|
| ecdsa_verify | 23.7 | 22.3 | **0.94x** |
| ecdsa_sign | 17.2 | 16.1 | **0.94x** |
| group_add_var | 0.170 | 0.160 | **0.94x** |
| group_double | 0.0730 | 0.0699 | **0.96x** |
| ecdh | 23.1 | 22.5 | **0.97x** |
| group_add_affine | 0.140 | 0.136 | **0.97x** |
| field_mul | 0.0111 | 0.0109 | **0.98x** |
| field_sqr | 0.0102 | 0.0102 | 1.00x |
| group_add_affine_var | 0.119 | 0.119 | 1.00x |
| field_inverse_var | 1.00 | 1.03 | 1.03x |
| scalar_inverse_var | 1.01 | 1.04 | 1.03x |
| ec_keygen | 11.0 | 11.3 | 1.03x |
| ecdsa_recover | 24.8 | 26.7 | 1.07x |
| group_to_affine_var | 1.05 | 1.12 | 1.07x |
| scalar_mul | 0.0310 | 0.0432 | 1.39x |
| scalar_split | 0.126 | 0.203 | 1.61x |
| field_inverse (const time) | 2.17 | 1.75 | 0.80x* |
| scalar_inverse (const time) | 2.19 | 1.74 | 0.79x* |

**Signing, verification and ECDH are all faster than the C library**, by 3-6%.
Key generation is within 3% and recovery within 7%.

The two rows marked `*` are not like-for-like: libsecp256k1's constant-time
inversion declares its divstep condition variables `volatile`
(`modinv64_impl.h`), forcing a memory round trip 590 times per inversion to
stop the compiler turning the masking back into a branch. This port does not
replicate that, so it is doing strictly less work. The variable-time
inversions, where neither side pays that cost, are the honest comparison: 1.03x.

### What closed the gap

This started at 1.47x on verification. Four changes, in order of what they were
worth:

1. **Derive the endomorphism table instead of building it.** `lambda*(x, y)`
   is `(beta*x, y)`, so the second table of odd multiples is one field
   multiplication per entry rather than a second build with its own inversion.
   Worth about 6 us — by far the largest single win, and it also removed the
   `to_ge_var` that used to be needed to reach the affine point.
2. **Build tables on a shared z** (`_odd_multiples_globalz`). Converting a
   16-entry table to true affine coordinates costs a field inversion plus about
   five multiplications per entry; keeping the whole table in one scaled frame
   and folding that frame into the accumulator's z at the end costs neither.
   Worth about 2 us, and it applies to `ecmult_const` too.
3. **`@always_inline` on the field, group and variable-time inversion hot
   paths.** Worth about 2 us in total, and it is what moved `field_mul`,
   `group_double` and `group_add_var` from slightly behind C to slightly ahead.
4. **A wider window for G** (8 to 12 bits), and a variable-time
   `normalizes_to_zero`. Perhaps 1 us between them.

Two things that were tried and did not help, recorded so nobody repeats them:
unrolling `_mul_512` with `comptime for` (no measurable difference — the
compiler was already doing it), and inlining the *shared* safegcd helpers,
which sped up the variable-time inversion but cost the constant-time one 50%,
and signing pays that on every call.

### What is still slower

* **`scalar_mul` at 1.39x and `scalar_split` at 1.61x.** The C library uses a
  three-word comba accumulator for the 512-bit product where this port uses a
  simple schoolbook loop with 128-bit intermediates. `scalar_split` calls into
  it five times, which is why it tracks. Neither is on a hot enough path to
  have been worth rewriting yet — verification does two scalar multiplications
  against roughly 150 field multiplications.
* **`ecdsa_recover` at 1.07x**, which is mostly `ecmult` plus a square root;
  the square root is at parity, so this is the last of the `ecmult` gap.

`bench/bench.mojo` chains each iteration's output into the next input. Without
that the optimizer hoists loop-invariant calls straight out of the timing loop:
an earlier version of this table reported `field_sqrt` at 0.01 us and
`field_normalize` at 0.00, both of which were measuring nothing.

## GPU

| Workload | Batch | ops/sec | vs 1 CPU core |
|---|---:|---:|---:|
| k*G (CPU, 1 thread) | – | 62,893 | 1.0x |
| k*G (GPU) | 4,096 | 177,994 | 2.8x |
| k*G (GPU) | 32,768 | 200,697 | 3.2x |
| ecdsa_verify (CPU, 1 thread) | – | 25,957 | 1.0x |
| ecdsa_verify (GPU) | 4,096 | 27,518 | 1.1x |
| ecdsa_verify (GPU) | 16,384 | 45,301 | 1.7x |

Batches below about a thousand items are slower than the CPU — the launch and
transfer overhead dominates. The speedup only appears once there is enough work
to fill the device.

### How the GPU path is built

Three things shaped it:

1. **Metal has no 128-bit integers.** The CPU representation needs 64x64→128
   products, so `gpu32.mojo` re-implements the arithmetic in eight 32-bit limbs
   with 64-bit accumulators. It is tested on the CPU against the same C vectors
   (`tests/test_gpu32.mojo`), so a maths bug can never be mistaken for a kernel
   bug.
2. **Kernels never invert.** They emit Jacobian points and the host finishes
   the batch with a single field inversion for the whole set (Montgomery's
   trick). Verification avoids inversion altogether by comparing `x*z^2`
   instead of normalising, and the per-signature `1/s` is computed host-side
   for the entire batch at once.
3. **No lookup tables inside kernels.** A windowed ladder needs a dynamically
   indexed array of points, which Metal puts in per-thread memory rather than
   registers. Measured on an M2, plain double-and-add over the two GLV halves —
   everything in registers — beat a 4-bit window by about 30%.

Scalar arithmetic stays on the host entirely; kernels only read scalar bits.

### Caveats

**The GPU path is variable time.** The risk this creates is easy to state
wrongly, so precisely: it is not that a key in GPU memory is more exposed than
one in RAM — it is not. It is that the GPU kernels *branch on* and *index
memory with* secret-dependent values, where the CPU path does neither:

```mojo
# CPU — scans every table entry, selects with cmov
for j in range(GEN_ENTRIES):
    sel.x.cmov(e.x, j == digit)
acc = _gej_cmov(acc, added, digit != 0)

# GPU — branch and address both depend on the scalar
if digit != 0:
    acc = acc.add_ge(load_ge(table, b * 16 + digit))
```

An attacker who cannot read your memory but can observe the computation —
cache timing, memory access patterns, wall-clock — recovers scalar digits from
the second form. For ECDSA that is unusually dangerous: leaking a few bits of
each per-signature nonce across a few dozen signatures recovers the long-term
key by lattice attack. You do not have to leak the key itself.

So: use the GPU path where the scalars are public, or where no adversary can
observe the machine. Do not put it behind a signing service on shared
hardware. On a laptop with nothing untrusted running, it matters much less.

On the CPU side, the operations libsecp256k1 keeps constant time are written
branch-free here too: `Scalar.cond_negate`, `is_high` and `check_overflow` use
masks rather than `if` or short-circuiting `and`/`or`, table lookups in
`ecmult_const` are linear scans with `cmov`, and a zero window digit is
discarded with a conditional move rather than skipped. Secrets are also wiped
after use — the nonce, `1/k`, the RFC 6979 DRBG state, the hash block buffers —
through the volatile stores in [`src/secp256k1/scrub.mojo`](src/secp256k1/scrub.mojo),
because a plain assignment is a dead store the optimizer deletes.
`tools/check_scrub.sh` proves that at the assembly level and runs as part of
the suite:

```
naive wipe    : 0 store instructions (deleted by the optimizer)
Scalar.clear(): 4 store instructions (one per limb)
```

None of this has been checked against the generated assembly beyond that one
probe, and nothing stops the optimizer reintroducing a branch elsewhere. Treat
it as best-effort, not as an audited guarantee.

Metal silently skips a kernel whose launch configuration is too large for the
device, leaving the output buffer zeroed — which for verification reads as
"every signature is invalid". `GpuBatch` runs a known-answer check at
construction so that shows up as an error rather than a wrong answer. The
default block size of 32 was measured, not guessed; 512 triggers exactly this
failure on an M2.

## What is not implemented

Schnorr signatures (BIP 340), ElligatorSwift, silent payments, the
`_preallocated` context API, and the lax DER parsers. The core — field, scalar,
group, ECDSA with recovery, ECDH, key tweaking — is complete.
