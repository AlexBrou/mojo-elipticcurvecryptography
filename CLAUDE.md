# CLAUDE.md

Notes for working in this repository. The README is for users of the library;
this is for whoever is changing it.

## What this is

A port of [libsecp256k1](https://github.com/bitcoin-core/secp256k1) to Mojo:
field and scalar arithmetic, group operations, ECDSA with recovery, ECDH, key
tweaking, plus a GPU path for batch work and a C ABI for other languages.

It is a **derivative work** of libsecp256k1 — the algorithms are ports of its
implementation and the test vectors are generated against it. LICENSE carries
Pieter Wuille's copyright notice as the MIT terms require. Do not remove it.

## Commands

```
git submodule update --init --recursive   # required: hashing lives in a submodule
./run_tests.sh                            # everything, ~15 min (the GPU tests are slow)
SECP256K1_SKIP_GPU=1 ./run_tests.sh       # skip the GPU tests
./tools/fetch_reference.sh                # clone + build libsecp256k1 (for interop and benchmarks)
./bench/compare.sh                        # benchmarks side by side with C
./tools/check_format.sh                   # mojo format, as a check
./tools/check_warnings.sh                 # compiler warnings as errors
./examples/build_python.sh                # build the Python extension and run its example
```

Every `mojo` invocation needs `-I . -I src -I vendor/mojo-sha256/src`. Missing
the third is the usual cause of a confusing "unable to locate module" error.

## Layout

```
src/secp256k1/
  field.mojo      GF(p), 5x52 limbs. Magnitudes as in libsecp256k1's field_5x52.
  scalar.mojo     Z/nZ, 4x64 limbs. Always fully reduced.
  modinv.mojo     safegcd inversion, port of modinv64.
  group.mojo      Ge (affine) and Gej (Jacobian).
  ecmult.mojo     k*G, k*P, na*A + ng*G. The performance-critical file.
  ecdsa.mojo      sign / verify / recover / DER.
  api.mojo        Secp256k1 — the type end users hold.
  scrub.mojo      volatile wipes.
  gpu32.mojo      the same arithmetic in 32-bit limbs, for GPU kernels.
  gpu.mojo        GPU kernels and the batch host API.
ffi/capi.mojo             C ABI (opaque handle, 1/0 return codes).
ffi/secp256k1_mojo.mojo   native CPython extension module.
vendor/mojo-sha256/       SHA-256, HMAC, RFC 6979. Git submodule, pinned.
tests/vectors/            generated by tools/gen_vectors.c against the C library.
```

## The invariant that matters

**Everything is checked against libsecp256k1, not against itself.**
`tools/gen_vectors.c` includes the C library's internal headers and dumps
vectors for every layer — field, scalar, group, ecmult, ECDSA. Those are
committed in `tests/vectors/`.

If you change an algorithm, the vectors are the oracle. If you need new
vectors, extend `gen_vectors.c` and regenerate (the README has the compile
line) rather than writing expected values by hand.

`examples/use_from_c.c` links **both** libraries into one process and compares
results directly, including that signatures come out byte-identical. It runs as
part of `run_tests.sh` when the reference is built.

## Traps this project has already hit

Read this section before optimising or benchmarking anything.

**Benchmarks measuring nothing.** With a loop-invariant input the optimizer
hoists the call straight out of the timing loop. This produced a table where
`field_sqrt` read 0.01 us (real: 2.86) and `field_normalize` read 0.00. Every
loop in `bench/` now chains its output into the next input; keep it that way.

**Benchmarks comparing different things.** `group_add_affine` was timing the
*constant-time* `add_ge` against C's *variable-time* `gej_add_ge_var`, which
made the port look 19% slower than it was. Check what the C benchmark actually
calls (`src/bench_internal.c`) before trusting a ratio.

**Optimising to the reference instead of the hardware.** SHA-256 sat at 1.9x
"the C library" for a while because libsecp256k1 ships portable C with no
hardware backend. Using the ARMv8 crypto extension is 6x faster than portable
software. The reference's constraints are not necessarily yours.

**`mut self` is not faster than returning a value.** Measured: rewriting
`double` and `add_ge_var` against `mut self` made them 1-9% *slower*. The
return-value optimization already writes into the caller's storage, and value
semantics give the optimizer better aliasing information.

**`@always_inline` matters a lot here** — worth about 2 us on verification
across the field, group and variable-time inversion paths. But it is not free:
inlining the *shared* safegcd helpers sped up the variable-time inversion and
cost the constant-time one 50%, which signing pays on every call. Measure both.

**Dead stores get deleted.** Wiping a secret with `x = 0` compiles to nothing.
`scrub.mojo` uses volatile stores; `tools/check_scrub.sh` proves it at the
assembly level and runs in the suite.

## Mojo specifics

Mojo 1.0 differs sharply from what a pretrained model writes. `fn` is gone
(everything is `def`), `alias` is `comptime`, stdlib imports need the `std.`
prefix. The `mojo-syntax` skill in `~/.claude/skills/` is the correction layer;
read it before writing Mojo.

Beyond that skill, things this project ran into:

- `InlineArray`/`Array` is not `ImplicitlyCopyable`. A struct with one as a
  field cannot synthesize an implicit copy constructor — either use named
  scalar fields (what `Fe` and `Scalar` do) or write the copy/move constructors
  by hand (what `gpu32.mojo` does).
- `InlineArray` has no positional constructor: `var a: InlineArray[T, N] = [x, y]`.
- A module-scope `comptime` array cannot be indexed at runtime; use
  `materialize[TABLE]()` once inside the function.
- `Span[UInt8]` fails to infer its origin. Write `Span[UInt8, _]`.
- `fn`, `out`, `ref`, `var` are reserved and cannot be used as identifiers,
  including as local variable names.
- Inside a struct body, struct parameters must be `Self`-qualified.
- Hardware intrinsics: `llvm_intrinsic["llvm.aarch64.crypto.sha256h", W](...)`
  from `std.sys.intrinsics`. Names come from LLVM's `IntrinsicsAArch64.td`.
- Volatile store: `Pointer(to=x).unsafe_store[volatile=True](0, value)`.

## GPU

Kernels cannot use 128-bit integers — Metal's backend rejects them — which is
why `gpu32.mojo` reimplements the arithmetic in 32-bit limbs. It is tested on
the CPU against the same vectors (`tests/test_gpu32.mojo`) so an arithmetic bug
can never be mistaken for a kernel bug.

Three things to know:

- **Metal silently skips a kernel** whose launch configuration is too large,
  leaving output buffers zeroed rather than erroring. `GpuBatch.__init__` runs
  a known-answer self-test for exactly this reason. Keep it.
- **`from_bytes[big_endian=True]` ignores the flag on Metal.** Use an explicit
  `byte_swap`. This produces plausible garbage, not a crash.
- **`block_size` was measured, not guessed.** 32 for the secp256k1 kernels on
  an M2; above 256 the kernel silently does not run.

The GPU path is variable time by design and is for public data. The risk is not
that VRAM is less safe than RAM — it is that the kernels branch on and index
memory with secret-dependent values, where the CPU path uses `cmov`.

## Constant time

The operations libsecp256k1 keeps constant time are written branch-free here
too: `cond_negate`, `is_high`, `check_overflow` use masks rather than `if` or
short-circuiting `and`/`or`; `ecmult_const` scans tables linearly with `cmov`
and discards a zero digit with a conditional move.

This is best-effort and unaudited. If you touch those paths, keep them
branch-free, and do not introduce an early return that depends on a secret.

## Not implemented

Schnorr/BIP-340, ElligatorSwift, silent payments, the `_preallocated` context
API, the lax DER parsers. The GPU batch API is not exposed over the C ABI.
